# PDF 合并

把任意多的 PDF 按指定顺序合并成一个 PDF 的工具站。Vue 3 + FastAPI + PyMuPDF，纯 Python 依赖，不需要 Ghostscript、不需要 Windows 打印子系统。

## 它解决的问题

合并 PDF 本身不难，难的是**带数字签名的 PDF**。这类文件里的签名图样（签章、签名栏）是注释对象，直接 `insert_pdf` 合并后往往就消失了 —— 用户拿到一份看起来就不对劲的合同。

这个工具的处理方式是：**检测到签名就把该文件的注释与表单字段「烤」进页面内容流**（`PyMuPDF` 的 `bake()`），再参与合并。结果是页面外观与原件逐像素一致（冒烟测试里有这条断言，实测差异为 0），而原有的矢量与文本层完全保留。bake 不可用时自动退回栅格化，栅格化永不失败。

**明确取舍**：签名的**外观**被保留，签名的**密码学有效性**必然失效 —— 这是任何合并/打印/转换操作都无法避免的，合并后的文件已经不是原签署对象了。这一点在界面上对用户是明说的。

## 快速开始

```bash
# 1. 后端依赖
python -m pip install -r requirements.txt

# 2. 前端构建（已随仓库提交，改前端时才需要重新执行）
cd frontend && npm install && npm run build && cd ..

# 3. 启动
python -m backend
```

打开 `http://127.0.0.1:8000`。接口文档在 `/api/docs`。

### 开发模式

两个终端，前端带热重载与 `/api` 代理：

```bash
python -m backend --reload          # 后端 :8000
cd frontend && npm run dev          # 前端 :51229（监听 0.0.0.0）
```

前端开发服务器绑定在 `0.0.0.0:51229`，局域网内其他机器可以直接用 `<本机IP>:51229` 打开。后端默认也监听 `0.0.0.0:8000`；即使不是，`/api` 的代理由 dev server 自己发起，别的机器访问时前端照样能拿到接口。

## 部署到另一台机器

目标机器**只需要 Python 3.10+**。`frontend/dist/` 是构建产物且已提交入仓库，所以目标机器不必安装 Node。

```bash
conda create -n pdfMerge python=3.10
conda activate pdfMerge
pip install -r requirements.txt
python -m backend
```

代码里**没有任何绝对路径常量**，全部配置项都能用环境变量覆盖：

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `PDFMERGE_STORAGE` | `./storage` | 存储根目录（归档、产物、缓存、审计库都在下面） |
| `PDFMERGE_HOST` | `0.0.0.0` | 监听地址 |
| `PDFMERGE_PORT` | `8000` | 监听端口 |
| `PDFMERGE_CONCURRENCY` | `2` | 同时运行的合并任务数。**这是内存上限的旋钮** |
| `PDFMERGE_MAX_FILE_MB` | `200` | 单个文件上限 |
| `PDFMERGE_MAX_FILES` | `50` | 单次文件数上限 |
| `PDFMERGE_MAX_TOTAL_MB` | `1024` | 单次总量上限 |
| `PDFMERGE_JOB_TIMEOUT` | `600` | 单任务超时（秒） |
| `PDFMERGE_RASTER_DPI` | `200` | 栅格化兜底路径的分辨率 |
| `PDFMERGE_OUTPUT_RETENTION_HOURS` | `24` | 合并产物保留时长 |
| `PDFMERGE_THUMB_RETENTION_DAYS` | `30` | 缩略图缓存保留时长 |
| `PDFMERGE_ARCHIVE_RETENTION_DAYS` | `0` | 归档保留天数，**0 = 永久**（见下文） |

启动脚本 `start.bat`（Windows）与 `start.sh`（Linux / macOS）已提供。

```

  dist/              构建产物，已提交入库

```

### 处理路径

每个源文件按是否需要保住签名外观分流，三条路径的输出质量依次递减：

| 路径 | 触发条件 | 效果 |
|---|---|---|
| `direct` | 无签名 | 直接 `insert_pdf`，最快，保矢量保文本层 |
| `bake` | 检测到签名，或用户勾选强制 | 注释烤进内容流，外观一致且保住文本层与矢量 |
| `raster` | bake 失败时兜底 | 整页栅格化重建，外观保住，文本层丢失 |

签名检测的判据取自 PDF 规范：`/SigFlags`、AcroForm 里的 `/Sig` 字段、`/Perms` 中的 `/DocMDP`。不做图像启发式 —— 误报率太高。检测必然有漏报（盖章图片、已被拍平过的旧签名、畸形文件），所以界面上留了「强制保留签名外观」开关兜底。

**为什么不用虚拟打印**：字面意义的虚拟打印之所以能保住签名外观，唯一原因是它把整页光栅化了 —— 而 `bake` / `raster` 在纯 Python 里达到同样的视觉结果，不需要打印子系统、不需要 pywin32、不锁死 Windows。保外观的目标照做，打印作为手段被替换掉。

### 合并语义

- **顺序**：拖拽调整，页面严格按该顺序拼接
- **书签**：每个源文件生成一个顶层书签（以原文件名命名），文件原有的目录结构下移一层保留在其下
- **页面尺寸**：不归一化，A4 与 Letter 各保持原样。把 Letter 强行装进 A4 是排版行为，不是合并
- **加密文件**：明确报错并在界面上点名该文件，**绝不静默跳过** —— 静默跳过会让用户拿到缺页的文件而不自知
- **页码范围**：不做。这是合并工具不是编辑工具

## 留档与审计

出于合规要求，**所有上传的原件都会保留**，按「原文件名 + 时间戳」重命名后存放：

```
storage/archive/2026/09/22/合同正本__20260922-143052__a1b2c3d4.pdf
```

命名里额外带了一个 job 短 ID。纯「文件名 + 时间戳」会在一个真实场景下互相覆盖：用户从两个不同文件夹拖进两个都叫《合同.pdf》的文件。留档系统里发生覆盖是致命缺陷，多这 8 个字符买的是「永不覆盖」。

审计日志在 `storage/audit.sqlite3`，两张表：

- `jobs` —— 任务级：时间、来源 IP、User-Agent、文件数、总字节、输出名、状态、处理路径统计、耗时、错误
- `job_files` —— 文件级：原始文件名、归档文件名、归档路径、**sha256**、字节数、页数、是否含签名、实际处理路径、排序位置

`sha256` 是非抵赖锚点：将来若要回答「这份文件有没有被改过」，哈希是唯一能回答的东西。

**判定点是「用户提交了」，不是「这件事成功了」。** 文件在上传完成的一刻就进入归档区。用户从此再也没回来点「合并」，原件同样留存 —— 放弃和失败恰恰是留档最该覆盖的情形。

**归档保留期默认是「永久」**（`PDFMERGE_ARCHIVE_RETENTION_DAYS=0`）。这个默认值是刻意的：留档系统的自动删除是危险默认值。合规要求的「至少 N 年」不等于「到期就删」，到期销毁应当是显式的人工动作，不该由代码在某个凌晨悄悄执行。确有强制销毁期限时，把它设成正数即可。

**前端用户对留档零可见**：界面文案不提、API 响应里没有相关字段、错误信息不带路径、下载文件的元数据里没有服务器路径。这一条不是靠「写代码时记得删字段」保证的 —— 客户端只用 `job_id` 和随机文件 id 定位东西，归档路径**从来没进过响应体**。端到端测试里有一组专门的断言守着它。

服务端控制台日志与 `storage/` 目录本身当然会提到归档，那是运维视角。

### 生命周期

| 内容 | 寿命 |
|---|---|
| 上传原件 | 永久（除非显式配置保留天数） |
| 栅格化中间产物 | 任务结束即删，不跨重启存活 |
| 合并结果 | 24 小时 |
| 缩略图缓存 | 30 天（按内容 sha256 命名，重复上传不重复渲染） |

## 测试

```bash
python scripts/smoke_test.py     # 合并管线：夹具自造，逐条断言
python scripts/e2e_test.py       # 端到端：真起服务，真发 HTTP
```

两个脚本都用标准库 + PyMuPDF，零额外依赖，任何目标机器上都能直接跑。

`smoke_test.py` 里最重要的一条是**像素级外观断言**：把带签名的源文件的一页与合并结果里对应的一页渲染成位图逐像素比较。签名图样「有没有消失」这个用户最关心的问题，只有这个测试能回答 —— 检查注释数量、检查内容流长度都只是代理指标。实测平均像素差为 `0.000000`。

`e2e_test.py` 覆盖 HTTP 契约、留档落盘与命名、审计入库、排序生效、错误路径，以及那组「响应体不得泄漏留档」的断言。

## 已知限制

- 任务状态存在内存里，**服务重启后前端轮询会 404**，需要重新上传。（归档与审计不受影响，它们落盘。）
- 不做页码范围选择、页面重排、水印、压缩 —— 那是另一个产品。
- 单个任务串行处理文件，靠任务级并发（默认 2）横向扩展。这是为了给栅格化的内存峰值封顶：2 个 200MB 文件同时栅格化，峰值可能到 GB 级。
